# Update behavior: what gets propagated, what stays untouched

This document describes how wbforms turns an edit into a Wikibase write, so that
the guarantee *"on edit only actual changes are propagated and existing values stay
untouched"* is auditable. It also records two issues that were investigated.

## Write path

```
HTTP PUT
  → FastAPI router (generated by codegen/fastapi_gen.py)
  → handle_item_update / handle_statement_update   (api/utils.py)
  → wikibase.get_item(qid)                          (read the full item, incl. qualifiers)
  → update_item_from_model / update_qualified_statement_from_model  (wbgenerator.py, mutate in place)
  → wikibase.write_item(item)                       (item.write() persists the whole entity)
  → get_model_from_item / get_item_statement_by_id  (re-read for the response)
```

Both update flows are **read-modify-write**: the existing item is fetched in full
(`Wikibase.get_item`, `wikibase.py`), mutated in memory, then written back. Anything
not touched in memory is written back unchanged.

## Item update (`update_item_from_model`, `wbgenerator.py`)

The function iterates **`model.model_fields_set`** — i.e. only the fields actually
present in the request body — not every field of the model. A partial update therefore
only ever touches the properties the client sent.

| Field kind | Behavior on update |
|---|---|
| Single-value direct property | Mainsnak replaced in place on the existing claim (or one added if absent). |
| MonolingualText direct property | Only the matching-language claim is replaced; other languages preserved. |
| Multi-value direct property (list) | All claims for that property removed, then re-added (`_remove_property_claims` + `FORCE_APPEND`). |
| Statement-reference field (e.g. `authors`) | All statements for the subject property removed, then rebuilt from the payload (wipe-and-rebuild). |
| `<field>_sources` | Second pass re-attaches reference blocks to the matching direct-property claims. |
| Field **not** in `model_fields_set` | Untouched. |

**Key consequence:** because a field that is absent from the request is never visited,
editing a plain property does **not** disturb qualified statements or their qualifiers.
The wipe-and-rebuild branch only runs for a statement-reference field when that field is
explicitly part of the request body.

## Statement update (`update_qualified_statement_from_model`, `wbgenerator.py`)

Targets a single statement by `statement_id` and is selective per field:

- The mainsnak (statement subject) is replaced only if provided.
- For each qualifier field **in `model_fields_set`**, that qualifier's snaks are cleared
  and re-added; qualifiers for fields not in the request are preserved.
- References (`sources`) are replaced wholesale only when `sources` is in the request.
- Other statements on the item are never touched (they have different claim ids).
- Stale `statement_id`s (e.g. case differences or a replicated backend) are re-resolved
  by statement identity before failing (`_statement_ids_equal`, the
  `StatementNotFoundError` fallback in `handle_statement_update`).

## Frontend contract

- `EntityEditor.js` keeps direct fields in `pendingData` and **excludes**
  `statement_list` fields from it; qualified statements are edited separately and
  committed through their own statement endpoints (`pendingStatements`).
- Therefore the item `PUT` body never contains statement-reference fields — reinforcing
  the backend guarantee above.
- `CommitDialog.js` only issues the item `PUT` when item-level fields or sources actually
  changed, so a statement-only edit performs no full-item write.

## Investigated issues

### 1. "Saved! QID: (unknown)" / no reload after a statement-only edit — fixed

When only a qualified statement changed, no item `PUT` ran, so the commit result was
`undefined`; the frontend emitted that, showed `QID: (unknown)`, and dropped the loaded
item. Fix: after a commit, `CommitDialog.js` re-fetches the full entity by QID and emits
that, and `EntityEditor.js` re-applies it to the whole form (shared `applyEntity` helper),
so fields, sources, and statement tables all reload. This also makes a normal item edit
reflect statement ops that ran after the item write.

### 2. Direct-property edit wiping qualifiers — not reproduced

Investigation found no code path that wipes qualifiers on untouched statements during a
direct-property edit: `update_item_from_model` only visits `model_fields_set`, the
frontend never sends statement fields in the item body, and `item.write()` persists the
full in-memory item (with its loaded qualifiers). This is locked in by
`tests/test_wbgenerator_qualifiers.py::TestItemUpdatePreservesStatements`, which builds a
paper with a qualified author statement, updates only a direct property, and asserts the
author statement id and its qualifiers survive. Earlier hardening of the statement path
(qualifier mutate-during-iteration fix; stale statement-id re-resolution) remains in
place.
